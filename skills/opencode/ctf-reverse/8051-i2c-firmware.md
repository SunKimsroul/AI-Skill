# 8051 Firmware and I2C Peripheral-Model Workflow

## Scope

Use this for supplied 8051/MCS-51 firmware, C source, Intel HEX, Verilog peripheral model, or a local CTF emulator. Treat firmware and hardware-model code as one state machine; a lock or access-control decision in the peripheral may matter more than the CPU instructions.

## Reconstruct the Board

1. Preserve the Intel HEX addresses and establish whether the artifact is code, EEPROM data, or a loader payload. Build an 8051-aware view of code space, internal RAM, special-function registers, and port bits.
2. Map firmware port writes to peripheral signals. Identify serial clock/data, chip select, power/reset, and UART-output bits from source, headers, symbols, or the Verilog module.
3. Read the peripheral model as a protocol state machine: start condition, device address, memory address, read/write direction, acknowledgement, stop condition, page boundary, and lock transitions.
4. Test the normal firmware transaction in the supplied local emulator. Record the exact event sequence and state after each edge before testing alternative protocol paths.
5. Examine whether the model distinguishes a stop from a repeated start, resets a pointer only on one of them, applies locks by page rather than whole-device, or checks authorization before updating an address. Validate only against the supplied CTF model.

# Compile a local 8051 fixture when C source and SDCC are supplied.
sdcc firmware.c
objcopy -I ihex -O binary firmware.ihx firmware.bin

## Validate the Result

- Confirm the local emulator receives the expected start/address/ACK/data sequence.
- Require the normal firmware behavior to remain unchanged before accepting an alternate transaction interpretation.
- For a recovered byte range, show its peripheral address, page/lock state, and the exact trace that made it readable.

**Source pattern:** Google CTF 2019, `flagrom` ([writeup](https://blog.atx.name/google-ctf-2019/)).
